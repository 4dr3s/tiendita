# ADR-0002: Tenancy and data isolation

**Status:** Accepted, 2026-09-22

## Context

TIENDITA v2 is a multi-tenant SaaS: many small stores share one deployment. Cross-tenant leakage
is the worst failure this system can have, because one bug exposes every customer at once.

Three things make the decision non-obvious:

- **Better Auth owns the tenancy tables.** Its organization plugin creates `organization`,
  `member`, `invitation`, `team` and `teamMember`, and adds an active-organization reference to
  `session`. Those tables are the source of truth for who belongs to which organization, and they
  are generated into our Prisma schema by a third-party CLI.
- **Postgres row level security needs a context that the queries must set.** A policy keyed on a
  session variable returns zero rows when the variable is unset, which is exactly what "fails
  closed" means — and exactly why it breaks a library that does not set it.
- **There is more than one writer.** Besides the request path, background workers (the outbox
  poller, Telegram notifications, OCR jobs) write tenant-scoped data, and they do not pass through
  the request guard.

## Decision

**A shared schema, with mandatory application-level organization scoping as the primary contract,
plus Postgres row level security on business tables.**

- **Application scoping is the contract, not a convention.** Repository and gateway signatures
  require an `organizationId`. There is no "load everything" path, so omitting the tenant
  dimension is a type error rather than a code-review comment.
- **`organizationId` is never trusted from the body or the URL.** The session is the source of
  truth; an organization in the request is a selection hint that must be cross-checked against
  membership. A mismatch fails closed.
- **Row level security covers business tables from the first one onward**, with a policy per
  tenant-scoped table comparing its `organization_id` to a per-transaction session variable, and
  `FORCE ROW LEVEL SECURITY` on a role without `BYPASSRLS` used by the API **and by workers**.
- **Row level security on Better Auth's own tables is deliberately deferred, with this reason
  recorded:** with the Prisma adapter the only available implementation would be giving those
  connections a `BYPASSRLS` role — a nominal guarantee rather than a real one — because Better
  Auth's queries do not set the session variable, so a policy keyed on it would return zero rows
  and break Better Auth itself. Those tables are governed by Better Auth's own guards plus the
  organization rule above.
- **`organization` and `member` are the tenancy source of truth.** A business table's
  `organizationId` is a foreign key to a table generated by another tool, and that is accepted
  deliberately rather than hidden.

## Consequences

**What it buys.** One migration stream and one schema to reason about, which is what a small team
needs. Prisma works without ceremony, and superadmin and analytics queries are ordinary queries.
Per-tenant cost is negligible and backup is trivial. The second enforcement layer protects the
path that actually ships cross-tenant bugs — a worker that never sees the guard — and it fails
closed by construction: with the session variable unset, every tenant-scoped query returns zero
rows.

**What it costs.** Every query must carry the tenant dimension, and that discipline is now
load-bearing for the primary layer. A policy mistake can fail silently in either direction: too
loose leaks, too tight breaks the application confusingly, and row-count semantics of bulk
operations under row level security have surprised many teams. Per-tenant lifecycle operations
(deleting or exporting one tenant's data) are not free — they are org-keyed deletes you build.
And the deferred decision above is debt: if Better Auth's tables ever become reachable by a path
that does not pass through its guards, the deferral has to be revisited.

**On the threat model, which is what reframed this decision.** Most literature arguing for row
level security assumes the client holds a database credential and queries directly — the
Supabase pattern. **In this architecture the browser never reaches Postgres; only the API does,
through Prisma.** Row level security here is therefore not protection against direct client
access. It is defence in depth against our own forgotten filters and against the worker path.
That is a real benefit, and it is a smaller one than the literature implies — which is precisely
why it is worth the cost on business tables and not worth a nominal bypass on the identity
tables.

## Alternatives considered

- **Row level security everywhere, including Better Auth's tables.** Chosen first, then narrowed
  after verification: with Prisma the only implementation is a `BYPASSRLS` role, which makes the
  policy decorative. Recorded here because the reasoning that rejected it is more useful than the
  conclusion.
- **Application scoping only.** Simpler and with nothing extra to maintain. It lost because the
  asymmetry is severe: one forgotten filter in one worker versus every tenant's data.
- **Schema per tenant.** Physical isolation, and dropping a tenant is dropping a schema. It lost
  on operations — migration fan-out across N schemas, segmented connection pooling, federated
  superadmin reads — and on a harder fact: with Prisma the tenant routing would have to be static
  rather than per-request, and Better Auth's tables live in the same schema, which removes most
  of the appeal.
- **Database per tenant.** The strongest isolation and the worst operational cost: provisioning
  and migrating per tenant, per-tenant clients, and per-tenant cost. It is the trap of
  accidentally building a managed-database product.

## Verification notes

**Verified in this repository:** Better Auth's organization plugin creates `organization`,
`member`, `invitation`, `team`, `teamMember` and touches `session`; `npx auth generate` writes
those tables into `schema.prisma`; and the documentation states that Prisma **schema generation is
supported while schema migration is not** — the CLI writes the schema and we run Prisma
migrations ourselves.

**Verified externally, with the caveat that the library claims were checked against current
documentation rather than executed:** that Better Auth's own queries do not set a row-level
security session variable, which is the basis for deferring policies on its tables. This should be
re-confirmed at implementation time, because it is the load-bearing fact behind the deferral.

**Reasoned, not verified:** that Prisma's multi-schema support cannot do dynamic per-request
tenant routing. This should be re-checked if schema-per-tenant is ever reconsidered.
